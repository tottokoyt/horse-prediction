# フェーズ3-2: バヌーシー追加が広い汎化に与える影響（11seed）

上記フェーズ3の単一seed結果はブレが大きかったため、10seed追加して計11seedで再集計した。

| | spearman合計（8クラブ） | 上位25%差分合計（8クラブ） |
|---|---|---|
| バヌーシーなし | 0.882±0.139 | 61.0±24.6 |
| バヌーシーあり（現行本番） | 0.760±0.179 | 27.6±16.0 |
| なしが勝った回数 | 9/11 seed | 10/11 seed |

**結論**: バヌーシーを学習に追加したことで、バヌーシー自身への予測（6seed CVで確認済み）は改善したが、
**他クラブ全体への汎化は一貫して犠牲になっている**（11seed中9-10回で「なし」が優勢）。
これはtclion/greenfで見たのと同じパターン。「自分自身の保留フォールドで良くなる」ことと
「他クラブ全体への汎化」は別物であることが、今回の広い未知クラブ集合での検証で明確になった。

**これは本番モデル（バヌーシー込み）に関わる重要な判断材料です。** バヌーシー自体が

# フェーズ5: 本番バグの発見と修正、今夜の検証結果への影響

## 発見した本番バグ（重要・修正済み・要デプロイ判断）

`app/predictor.py` の `_lookup()` 関数が、学習データに無い値（未知の
父馬・調教師・牧場・母父）に対して **ハードコードされた `GLOBAL_MEAN=80.0`**
を返していた。しかし学習時（`add_features`のfillna）は実際には
**その列の中央値（sire/trainer/farm/bms_nameいずれも93〜107%程度、
GLOBAL_MEAN=80.0とは大きく乖離）** を使っていた。

この不整合は、未知の値を含む予測（＝学習データが薄い小規模クラブほど
頻繁に発生）を系統的に歪めていた。**モデルA/B/Cすべてが影響を受ける
（`_lookup`は共通関数）が、特にモデルC（クラブ横断・多様な未知の
値が多い）への影響が大きいと推測される。**

### 修正内容
- `train_model_kakutoku.py`: 学習時に実際使われた中央値を
  `compute_fallback_medians()` で取り出し、モデルpklに
  `fallback_medians` として保存するように変更
- `app/predictor.py`: `_lookup()` が `fallback_medians`（モデル保存済み・
  最優先）→ stats_dfから中央値近似（次点）→ `GLOBAL_MEAN`定数（最終手段）
  の順で使うように修正
- モデルC再学習済み（学習時中央値: sire=93.5, trainer=97.8,
  farm=106.8, bms_name=102.8。旧GLOBAL_MEAN=80.0とは大きく違う）
- 単体テストで修正が正しく機能することを確認済み

**この修正はロジック的に明確な改善であり、本番へのデプロイを推奨します。**

## 今夜のCV検証への影響（重要な留保）

上記バグを追う過程で、**もう一つの問題**を発見した。`experiment_loco.py`
の `add_features()`（今夜のCV検証全般で使用）は、fillna(中央値)の
「中央値」を **処理中のデータフレーム自身** から計算する。学習セット
（2,800頭超）に適用すると安定した値になるが、**検証用の小さいテスト
フォールド（10〜11頭程度）に適用すると、そのフォールドだけの
数頭の中央値という、非常にノイズの大きい値になる**（実際に確認した例:
学習セット中央値は約97-98%だが、あるテストフォールドでは84.7%という
違う値になっていた）。

これは、今夜のCV検証（バヌーシー追加・tclion/greenf追加などの
「追加を検討」判定の根拠）に、**seedのブレとは別の追加ノイズ源**が
乗っていたことを意味する。複数seedで平均を取る対策はしていたが、
この「小バッチ中央値」の問題はseedを増やしても解消しない
（データの分割方法自体に起因するため）。

## 結論・推奨事項

1. **`predictor.py`のGLOBAL_MEANバグ修正は、単体で明確な改善なのでデプロイを推奨**
2. **今夜の「クラブ追加」判断（バヌーシー、tclion、greenf）は、上記ノイズ源が
   乗っている可能性があるため、当初思っていたよりも確度が下がる。**
   結論を覆すとまでは言えないが、追加の検証（`el.add_features`を
   小バッチ用に中央値の代わりに学習セット中央値を使うよう修正してから
   再検証する等）をしてから最終判断することを推奨する
3. 現行本番モデル（バヌーシー込み、アンサンブル）は変更していない。
   このセッションで得た知見をもとに、次回セッションで
   (a) GLOBAL_MEANバグ修正のデプロイ、
   (b) `experiment_loco.py`のadd_features小バッチ中央値問題の修正、
   (c) 修正後の環境でクラブ追加判断を再検証、
   の順で進めることを推奨する

## フェーズ11 追記: 根本原因を特定（collect_bosyu.pyのセレクタバグ、推定）

`collect_bosyu.py`の`collect_2020()`関数（346〜399行目）を確認したところ、
以下の箇所が原因である可能性が高いことが分かった:

```python
for item in soup.select("a[href*='/horse_bosyu/2020/']"):
```

シルク公式サイトの2020年募集一覧ページ内で、各馬の詳細ページへの
リンク（`/horse_bosyu/2020/...`）がページ構造上**複数箇所
（サムネイル画像・馬名テキスト・「詳細を見る」ボタン等）に
重複して存在していた**可能性が高い。このセレクタは馬ごとに
1つの`<a>`だけを想定しているが、実際には同じ馬について複数の
`<a>`要素がマッチし、その数だけ`rows.append(row)`が実行されて
しまったと推測される（他の年度は個人ブログ/PDF由来で、この
ようなHTML構造重複が起きないため無事だったと考えられる）。

実際に確認できた事実として、2020年の対象馬**全75頭が例外なく

系統的な重複であることと整合する。

**対応案**: `collect_2020()`内で`no`（またはhref自体）をキーに
重複除去してから`rows`に追加する、あるいは`df_bosyu`構築後に
`drop_duplicates(subset=["no"])`を挟む。

## フェーズ12: モデルA/Bも同じ重複バグの影響を受けるか検証（重要な違いを発見）

`train_model_v9.py`（モデルA）・`train_model_B_v7.py`（モデルB）も
`merged_train.csv`を直接読んでおり、`predictor.py`は実際にA/B/C
すべてを本番で読み込んで使っている。同じ重複バグの影響を
受けているはずなので、モデルAで同様の検証をした。

**結果は予想に反し、モデルCとは逆方向だった:**

| | 現行(重複バグ入り) | 修正版 |
|---|---|---|
| 上位25%回収率差分(5seed平均) | +29.0±1.4pt | **-12.9±7.4pt（悪化）** |
| 上位25%の200%超率 | 10.3%±0.0% | 4.6%±1.0%（悪化） |

**モデルCと違う結果になった理由**: モデルCは11クラブ+バヌーシー等
「プール全体」で学習するため、シルクの634→184頭への削減は
学習データ全体（2000〜3000頭規模）のごく一部の変化に過ぎない。
一方モデルA/Bは**シルクの行だけを直接学習・評価に使い、他クラブは
smooth_mean集計プールの補強にしか使っていない**（測尺
height/chest/cannon/weightなどシルク固有の特徴量を使っているため）。
このため、シルクの学習頭数が634→184頭（71%減）になることが
モデルA自体の学習サンプル不足に直結し、精度が悪化したと考えられる
（重複データは統計的には「情報量ゼロの水増し」だが、LightGBMの
木の分割の安定性という点では、たとえ水増しでも同じ分布のデータが
多い方が過学習しにくく安定する、という副作用があった可能性がある）。

**結論**: **「重複を消せば必ず良くなる」という単純な話ではない。**
モデルCについては強く修正・再学習を推奨するが、**モデルA/Bについては
同じ修正をそのまま適用すると悪化するため、別の対応が必要**
（例: smooth_meanのmin_samplesを調整する、シルク以外のクラブの
生データも直接学習に混ぜる設計に変更する、あるいはモデルA/Bは
このプロジェクト本来の目的（バヌーシー向けクラブ横断予測）には
そもそも不向きなので、優先度を下げてモデルCに一本化することを
検討する、等）。**モデルA/Bは今夜は変更していない。**

## フェーズ13（朝一の追加検証・重要な下方修正）: 最終候補モデルの真のLOCO再検証で、当初の「劇的改善」は再現しなかった

デプロイ前の最終確認として、最終候補モデル（シルク修正+tclion追加）を
既知11クラブ全部を1つずつ未知として扱う真のLOCOで検証した。
**1回目の実行ではベースライン（現行本番相当）の構築に不備があり
（`experiment_loco.load_combined()`を使ったため、実際の本番に
含まれる「バヌーシー」が抜けていた）、修正して再実行した。**

**修正後の結果（11クラブ、5 seed平均）**:
- spearman: 現行相当=0.067±0.061 → 最終候補=0.075±0.037
  （8/11クラブで改善、方向は一貫しているが効果量は小さい）
- 上位25%diff: 現行相当=6.5±6.1 → 最終候補=6.4±6.3
  **（5/11クラブでしか改善せず、平均はほぼ同じ＝実質改善なし）**

**これは、今夜これまで繰り返し使ってきた6クラブ
（yushun/turffight/hiroo/ygg/waraukado/insel）での評価
（spearman 0.34→0.67、上位25%diff -25.1→+66.5）とは大きく異なる、
はるかに控えめな結果である。** 11クラブ全数を使う、より偏りの少ない
検証の方が信頼できるため、**「シルク修正+tclion追加で劇的に改善する」
という当初の結論は取り下げる。**

## 何が起きたかの解釈

1. **6クラブ評価セットへの過剰適合の可能性**: 今夜同じ6クラブを
   何度も評価に使い回してきたため、たまたまその6クラブでは
   改善方向に強く出やすい特性があった可能性がある（多重比較的な
   選択バイアス）。11クラブ全数の方がノイズは残るものの、
   偏りは少ない。
2. **spearman相関は小さいながら一貫して改善**（8/11）しており、
   方向性自体は間違っていなさそう。ただし上位25%diff
   （実務上重要な「上位馬の実際の回収率」の指標）では
   はっきりした改善が見られなかった。

## 現時点での修正後の推奨

- **シルクの7重複バグ自体は、データとして明確に誤り**（同一行の
  単純な7倍複製、しかも高成績寄りに偏っている）なので、
  **データ品質の観点からは修正して当然**。ただし「修正すれば
  予測精度が劇的に上がる」という宣伝文句は取り下げ、
  「誤ったデータを正しくする、副作用として精度への影響は
  小さい〜中程度」という、より地に足の着いた位置づけに変更する。
- **tclion追加も同様、11クラブ全数では効果は小さめ**（spearmanのみ
  緩やかに改善）。見送るほどの根拠もないが、「劇的に良くなる」
  は言い過ぎだった。
- **今夜のうちに本番へ即デプロイすることは推奨しない。**
  むしろ、6クラブでの評価結果に引きずられて拙速に判断しかけた
  ことを反省点とする。もう少し広いクラブ集合・複数の評価軸
  （spearman以外にも、実際の回収率の絶対水準や的中率なども）で
  確認してから判断する方が良い。

## フェーズ14: log1p変換による目標値バグの修正（朝一で発見・修正・検証）

git commit直前の最終確認で、`_ensemble_kakutoku`の実際の出力（万円単位の
絶対額）を正しく検証したところ、**モデルCの予測がどの馬を入れても
ほぼ一定値（現行本番: 3305〜3325万円、狭い範囲に収束）にしかならない**
という、今夜の作業とは独立した重大なバグを発見した。

**原因**: 回帰目標値`kakutoku_man`（獲得賞金）が極端な右裾分布
（平均2919万円 vs 中央値610万円、上位1%の馬で総額の約25%を占める）
であるにもかかわらず、生の値のままhuber回帰の目的変数にしていた。
少数の超高額馬（デアリングタクト、リバティアイランドなど実在の
GI級名馬、kakutoku_man最大221,482万円）に予測が支配され、
実質的にほぼ定数を返す状態になっていた。**gitにコミット済みの
現行本番モデルでも同じ症状を確認したため、これは今夜以前からの
既存バグ**（血統・調教師・牧場の違いをほとんど反映しない予測に
なっていた）。

**修正**: `train_model_kakutoku.py`でhuber回帰の学習をlog1p(kakutoku_man)
に変更し、`app/predictor.py`の`_ensemble_kakutoku`で最終出力に
`expm1`をかけて実スケール（万円）に戻すよう修正。修正後、実際の
yushunクラブ実績馬10頭で試したところ、予測獲得賞金が150万〜2481万円
と、馬ごとに明確に変動するようになったことを確認（修正前は
2883〜2892万円でほぼ一定だった）。

## この修正込みでの真のLOCO再検証（11クラブ、5 seed）

| | spearman | 上位25%diff |
|---|---|---|
| 旧（今夜の変更前、実デプロイ状態） | 0.067±0.061 | 6.5±6.1 |
| 完全修正版（シルク重複修正+tclion追加+log1p変換） | **0.080±0.039** | **7.9±3.9** |
| 改善したクラブ数 | 7/11 | 6/11 |

spearman・diffともに平均は緩やかな改善（大きくはない）だが、
**両指標とも分散が大きく縮小**（diff: 6.1→3.9）しており、
予測の安定性・再現性が上がっている。

## 結論・最終推奨

この修正（log1p変換）は、**LOCOの集計指標への影響は緩やかだが、
「予測がほぼ一定値に潰れる」という質的なバグを直す、独立した価値の
ある修正**である。集計指標が劇的に改善しないからといって見送るべき
ものではない——そもそも予測値が意味をなしていなかった状態を、
最低限「血統・厩舎・牧場によって変動する」という状態に戻すもの。

**今夜の最終的な変更点（3点セット）**:
1. シルク募集データの7重複バグ修正（`merged_train.csv`更新）
2. tclionクラブを学習データに追加
3. kakutoku_manのlog1p変換（huber回帰の目的変数）

3点セットとも実装・ローカル検証済み。ユーザーの承認を得てから
git commit・pushする。
